# wabun

日本語技術文書の直訳調（翻訳調）を測定して情報を保存したまま日本語として書き直し、主張と根拠のつり合いを監査する Claude Code / Codex プラグイン。

AI が書く日本語はなぜか翻訳臭い——のに、「〜することができます」のような教科書的な直訳マーカーは見当たらない。この掴みどころのなさを対照実験で分解し、実験で差が出たマーカーを中心に検出器を組んだのがこのプラグインです（文体の敬体/常体混在チェックなど実験外の補助判定も少し含みます）。測定 → 書き直し → 再測定のループを回すので、翻訳条件に偏ったマーカーが同ジャンル書き下ろしの水準へ近づいたかを数値で確認できます。既に出力済みの文書にも使えます。

## インストール

### Claude Code

```
/plugin marketplace add happy-ryo/wabun
/plugin install wabun@wabun-marketplace
```

### Codex CLI

```bash
codex plugin marketplace add happy-ryo/wabun
codex plugin add wabun@wabun-marketplace
```

インストール後は、新しいセッションを開始してプラグインを読み込みます。

## 使い方

| 環境 | 推敲 | 主張監査 |
|---|---|---|
| Claude Code | `/wabun:suiko path/to/doc.md` | `/wabun:kansa path/to/doc.md` |
| Codex | `$wabun:suiko path/to/doc.md` | `$wabun:kansa path/to/doc.md` |

ファイルパスの代わりにテキストを貼り付けても、「さっきの出力を直して」でも動きます。判定の物差しは「書き下ろし水準」——同じ書き手が英語原文なしで日本語をゼロから書いたときのマーカー密度（後述の実験の C 条件で実測。レポートでは「C参照値」）——です。実際の合否は C 参照値そのものではなく、そこから翻訳調水準へ向けて余裕を持たせた「許容上限」で判定し、全マーカーが許容上限内なら測定結果を報告するだけで書き直しには進みません（上限内の文書を参照値へ寄せる過剰修正もしません）。

文体ではなく主張の中身を点検したいときは監査スキルを使います。断定と根拠のつり合い（範疇錯誤・過大一般化・交絡の脱落・主語の不在・未定義語）を文単位で点検し、指摘の一覧だけを返します。

測定だけならスクリプト単体で動きます。終了コードは 0（水準内）/ 1（測定可能な散文なし）/ 2（要修正あり）、引数エラーは 64、ファイルの読み込み失敗は 66 で、CI にも置けます。複数ファイルは個別に測定し、1 つでも超過なら 2 を返します。コーパスをまとめて測るときは `--aggregate` を付けます。

```bash
node skills/suiko/scripts/analyze.mjs doc.md
node skills/suiko/scripts/analyze.mjs --aggregate docs/*.md   # 連結して1回で測定
```

## 何を検出するのか — 実測に基づく設計

基準値は 2026-08 に行った対照実験に由来します。B / C / H は同一の技術題材（find / tar / ssh_config / git-rebase。H は和訳が存在した find / tar のみ）で、A だけは別題材の技術文書です。散文量は A / B / C が各約 1.5 万字、H が約 1.1 万字で、すべて同一パイプラインで測定しました。

- **A**: 文体指示なしで日本語の技術文書を書き下ろし（Redis キャッシュ設計、API レート制限、Git ブランチ戦略、PostgreSQL インデックス設計）
- **B**: 英語の man ページを渡して日本語化（AI 翻訳）
- **C**: B と同じ題材のリファレンスを日本語で書き下ろし（ジャンル統制）。本文で「書き下ろし水準」と呼ぶ基準値はこの群の実測値
- **H**: 人間翻訳（JM プロジェクトの和訳 man ページ）

### 実測値（1 万字あたり）

| マーカー | A 書き下ろし | C 同ジャンル書き下ろし | B AI 翻訳 | H 人間翻訳* |
|---|---:|---:|---:|---:|
| 受動「〜される」 | 15 | 41 | 80 | 49 |
| 文頭「これは/この文書は」 | 4.3 | 3.0 | 15.4 | 10.9 |
| モダリティ（してもよい 等） | 0.0 | 1.8 | 6.3 | 6.4 |
| 複合助詞（において 等） | 2.5 | 4.2 | 14.7 | 20.9 |
| および/または | 5.5 | 5.4 | 18.2 | 5.4 |
| 「〜場合」 | 23 | 29 | 58 | 45 |
| なお、/ただし、 | 0.6 | 0.0 | 5.6 | 6.4 |
| ことができ | 0.0 | 0.0 | 2.1 | 5.4 |
| という（和文の緩衝） | 4.9 | 1.8 | 0.7 | 8.2 |

\* H は日本語版 man が存在した find + tar の 2 文書。この 2 題材に揃えた B/C の値も傾向は同じです。

数値は付属スクリプトの現行版（折り返し接合・表除去を含む抽出器）でコーパスを再測定した値で、検出器の基準値と同じ物差しです。初期の測定では固定幅折り返しの泣き別れにより H のモダリティを 0.9 と大幅に過小計測しており、再測定で 6.4 に修正しました。この修正で「モダリティ硬直は AI 特有」という当初の結論は覆っています（下記 4 参照）。

### 適用例（before / after）

B 群の find の AI 翻訳（7 項目が許容上限超過）に、このスキルの手順（測定 → 事実チェックリスト抽出 → 書き直し → 再測定）を適用した実測です。

| マーカー | 適用前 | 適用後 | C 参照値 | 許容上限 |
|---|---:|---:|---:|---:|
| 受動「〜される」 | 90.9 | 0 | 41 | 55 |
| 文頭「これは/この文書は」 | 12.7 | 2.6 | 3.0 | 6 |
| モダリティ | 4.2 | 2.6 | 1.8 | 3 |
| 複合助詞 | 10.6 | 5.2 | 4.2 | 7 |
| および/または | 14.8 | 2.6 | 5.4 | 9 |
| 「〜場合」 | 63.4 | 0 | 29 | 38 |
| なお、/ただし、 | 6.3 | 0 | 0.0 | 2.5 |
| ことができ | 0 | 0 | 0.0 | 1.0 |
| という（緩衝） | 2.1 | 5.2 | 1.8 | 1.5（下限） |

判定は 7 項目超過 → 全項目許容上限内。事実チェックリスト 13 項目の突き合わせで情報の欠落がないことも確認しています。ただしこれは 1 文書・作者自身による適用の実測（n=1）で、効果の一般性を示すものではありません。

### 分かったこと

1. **俗説は外れる。** 「〜することができます」「を提供します」「しかしながら」は AI の出力にほぼ現れません（おそらく学習の過程で抑制されたのでしょう。機序は未検証です）。むしろ「ことができ」は人間翻訳の癖でした。動作の名詞化の密度も、測定した範囲（A と B の比較）では差がありませんでした。
2. **観測: 英語の義務的要素に対応する表現が翻訳で一斉に増える。** 主語スロット（→文頭「これは」、動作主なし受動）、if 節（→「場合」）、前置詞（→「において」）、接続詞（→「および」）、法助動詞（→「してもよい」）に対応するマーカーが、B 群で一貫して増えました。この一致から、本プラグインでは「原文構造の保存」を共通要因の有力な作業仮説として扱っています。
3. **受動の多さは半分冤罪。** 英語原文なしの A/C 比較で 15→41 まで上がります。翻訳を疑う前に文書種別を見る必要があり、警告閾値もそれを織り込んでいます（ただし A と C は題材も異なるため題材差を分離できず、C の書き下ろしにも学習経由で翻訳文体が混じりえます。純粋なジャンル寄与はこれより小さい可能性があります）。
4. **人間翻訳も同じ罠にはまる。** find/tar の H 標本では、文頭指示語・「場合」・複合助詞・モダリティが B と同方向に現れました（モダリティは当初 AI 特有と見えましたが、計測バグの修正で H にも同水準と判明しました）。人間翻訳一般への拡張は今後の検証課題です。この標本で AI に偏ったのは「および」・ジャンル水準を超える受動、そして「という」のような和文の緩衝装置の欠落でした。人間翻訳者は直訳語彙を残しつつ和文の呼吸を回復し、AI は直訳語彙を消したのに呼吸を回復しない——「マーカーが無いのに翻訳臭い」の正体はここにあるというのが作業仮説です。

### なぜ「書き直し」なのか

技術翻訳の忠実性ルール「原文の情報を削らない」は、検証コストの都合で「原文の構造を保存する」として運用されがちです。翻訳調の正体はこの構造の保存にある、というのが本プラグインの作業仮説です。そして、省略は誤訳として責められるのに直訳調は責められないという非対称があるかぎり、構造をなぞる訳し方が安全策として選ばれ続けます。だから語彙だけ入れ替えても、訳し方が変わらない以上、次の文書はまた翻訳調になります。

そこでこのプラグインは契約を変えます。**構造保存の翻訳ではなく、情報保存の書き直し。** 書き直しの前に元テキストから事実項目を抽出し、書き直し後にその一覧と突き合わせる。忠実性の検証を行単位の対応から事実単位の対応に付け替えることで、情報を落とさないルールと読める日本語を両立させます。

## 開発

テストは依存なしで動きます。

```bash
node --test
```

計数の仕様: 受動は「され+終止系」のみ数えます（連用形「〜され、」や五段動詞の「〜られる」は対象外）。基準値を測った物差しと検出器を一致させるためで、数え方を広げる場合は基準値も同じ物差しで測り直す必要があります。

## 制約

- 基準値は技術文書（リファレンス・設計文書）由来です。ジャンルが大きく違う文章（お知らせ、エッセイ）では閾値がずれます。
- マーカー名を引用している文書（このスキル自身など）は自己言及で誤検出します。
- 2000 字未満の対象では密度が不安定なため、スクリプトが警告を出します。
