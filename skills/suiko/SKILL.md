# 和文ポリッシュ: 直訳調の測定と書き直し

## 前提となる契約

このスキルの作業は「構造保存の翻訳」ではなく **「情報保存の書き直し」** である。

- 原文(または元の文書)が伝えている事実・条件・制約は 1 つも落とさない。
- 文の切れ目・語順・要素の対応は保存しなくてよい。むしろ積極的に組み直す。
- 忠実性の検証は行単位の突き合わせではなく、事実項目の突き合わせで行う。

この区別が重要な理由: 技術翻訳の「情報を削らない」ルールは、検証コストの
都合で「構造を保存する」として運用されがちで、それが直訳調の正体だから。
構造を保存する限り、語彙をいくら直しても翻訳調に戻る。

## 手順

### 1. 対象の取得

引数のファイルパス、貼り付けられたテキスト、または「さっきの出力」等で
指定された直前の生成物。テキストで渡された場合は一時ファイルに保存する。

### 2. 測定 (before)

```bash
node ${CLAUDE_SKILL_DIR}/scripts/analyze.mjs 対象ファイル
```

- 終了コード 2 = 要修正項目あり。レポートの表を要約してユーザーに見せる。
- 全項目 ok なら、その旨を伝えて終了してよい(過剰修正しない)。
- 2000 字未満の対象では密度が不安定。スクリプトの警告に従い、数値は
  参考扱いにして目視判断を優先する。

### 3. 事実チェックリストの抽出

書き直しの前に、元テキストから事実項目(仕様・数値・条件・警告・手順)を
箇条書きで抽出しておく。これが忠実性の検証基準になる。項目が多い長文では
セクション単位でよい。

### 4. 書き直し

フラグが立ったマーカーだけを直すのではなく、段落単位で内容を掴んで
日本語として組み直す。その際、検証済みの修正順:

1. **文頭の「これは/この文書は」を削る** — 指す先が直前にあるなら不要。
   英語の主語スロットの残骸で、最も判別力の高い翻訳調マーカー。
2. **「〜の場合」を散らす** — 「〜なら」「〜とき」、連体形への畳み込み。
3. **「および/または」を読点に** — 日本語の並列は読点で成立する。
4. **「において/に関して」を「で/は」に**。
5. **受動を能動に** — まず動作主を決める。決まれば能動に戻せる。
   不要なら「〜とする」「〜になる」。ただしリファレンス文体自体が
   受動を呼ぶので、基準値超過分だけ直せば足りる。全滅させない。
6. **モダリティを崩す** — 「してもよい」→「〜できる」、
   「なければならない」→「〜する」「〜してください」。
7. **緩衝を補う** — 「という」等が皆無で断定が連打されていたら適度に
   補い、文末のリズム(〜する。〜する。〜である。)の単調さを崩す。
8. **敬体/常体を統一** — 混在フラグが出ていたら文書の性格に合う方へ。

やってはいけないこと:
- コードブロック・コマンド・識別子・数値・URL を変えない。
- 技術的な内容の追加・削除・「改善」をしない(それは別の依頼)。
- マーカーをゼロにすることを目的化しない。基準値(書き下ろし水準)が目標。

### 5. 検証 (after)

```bash
node ${CLAUDE_SKILL_DIR}/scripts/analyze.mjs 書き直したファイル
```

- before/after のマーカー密度を表で対比して見せる。
- 手順 3 の事実チェックリストと突き合わせ、落ちた情報がないか確認する。
  落ちていたら書き直しに戻す。
- 元ファイルを直接上書きせず、diff を示すか別ファイルに書いてユーザーに
  選ばせる(明示的に上書き指示がある場合を除く)。

## 背景データ

基準値は 2026-08 の対照実験に由来する。3条件(A: 指示のみで書き下ろし /
B: 英語 man ページを翻訳 / C: 同題材を日本語で書き下ろし)+ 人間翻訳(H:
JM プロジェクトの和訳 man)、各群約 1.5 万字、技術リファレンス題材。

要点:
- 直訳調の主因は動作の名詞化ではなく、英語の義務的要素(主語スロット・
  if 節・前置詞・接続詞・法助動詞)の持ち込み。
- 受動の多さは約半分がリファレンスというジャンル由来。
- 文頭指示語・「場合」・複合助詞は人間翻訳者も同様に写す(翻訳一般の癖)。
  モダリティ硬直・「および」・緩衝装置の欠落は AI 翻訳に偏る癖。
- したがって「人間翻訳並み」は目標にならない。目標は書き下ろし水準。
