# 和文ポリッシュ: 直訳調の測定と書き直し

## 前提となる契約

このスキルの作業は「構造保存の翻訳」ではなく **「情報保存の書き直し」** である。

- 原文(または元の文書)が伝えている事実・条件・制約は 1 つも落とさない。
- 文の切れ目・語順・要素の対応は保存しなくてよい。むしろ積極的に組み直す。
- 忠実性の検証は行単位の突き合わせではなく、事実項目の突き合わせで行う。

この区別が重要な理由: 技術翻訳の「情報を削らない」ルールは、検証コストの
都合で「構造を保存する」として運用されがちで、それが直訳調の正体だから。
構造を保存する限り、語彙をいくら直しても翻訳調に戻る。

## 手順

解析スクリプトは、この `SKILL.md` と同じディレクトリにある
`scripts/analyze.mjs` を使う。実行環境に応じて次のパスを選ぶ。

- Claude Code: `${CLAUDE_SKILL_DIR}/scripts/analyze.mjs` を使う。
- Codex: 利用可能スキル一覧に示されたこの `SKILL.md` の親ディレクトリを
  絶対パスで取得し、その下の `scripts/analyze.mjs` を使う。

以下の Codex 用コマンドにある `<skill-dir>` は、実行前にその絶対パスへ
置き換える。`<skill-dir>` という文字列のままシェルへ渡してはならない。

### 1. 対象の取得

引数のファイルパス、貼り付けられたテキスト、または「さっきの出力」等で
指定された直前の生成物。テキストで渡された場合は一時ファイルに保存する。

### 2. 測定 (before)

Claude Code:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/analyze.mjs 対象ファイル
```

Codex:

```bash
node "<skill-dir>/scripts/analyze.mjs" 対象ファイル
```

- 終了コード 2 = 要修正項目あり。レポートの表を要約してユーザーに見せる。
  ただしフラグの実例が鉤括弧内の引用(マーカー名を論じる文など)なら実使用
  と区別し、引用のみで立ったフラグは書き直し対象にしない。
- 終了コード 1 = 測定可能な散文なし。対象の指定が正しいか確認する。
- 全項目 ok なら、その旨を伝えて終了してよい(過剰修正しない)。補助判定
  (敬体混在・緩衝の少なさ・詰まり)だけが出ている場合は、修正するか
  ユーザーに確認する。
- 複数ファイルは既定でファイル別に測定される。コーパスの一括測定には
  --aggregate を付ける。
- 2000 字未満の対象では密度が不安定。スクリプトの警告に従い、数値は
  参考扱いにして目視判断を優先する。

### 3. 事実チェックリストの抽出

書き直しの前に、元テキストから事実項目(仕様・数値・条件・警告・手順)を
箇条書きで抽出しておく。**否定・禁止・例外・規範強度(許可/義務/推奨)・
比率は必ず項目化する**——書き直しで最も反転・消失しやすい情報だからで
ある。これが忠実性の検証基準になる。項目が多い長文ではセクション単位で
よい。

### 4. 書き直し

フラグが立ったマーカーだけを直すのではなく、段落単位で内容を掴んで
日本語として組み直す。その際、検証済みの修正順:

1. **文頭の「これは/この文書は」を削る** — 指す先が直前にあるなら不要。
   英語の主語スロットの残骸で、最も判別力の高い翻訳調マーカー。
2. **「〜の場合」を散らす** — 「〜なら」「〜とき」、連体形への畳み込み。
3. **「および/または」は論理関係を保って言い換える** — 「および」は
   「と」「〜の両方」、「または」は「か」「〜のいずれか」。AND か OR か
   判別できないなら変更しない。読点だけの並列に畳んでよいのは AND と
   確定しているときだけ(読点は OR を表せない)。
4. **「において/に関して」を「で/は」に**。
5. **受動は動作主が一意に決まるときだけ能動に** — 原文か文脈から動作主
   が一意に決まるなら能動へ。決まらないなら「〜とする」「〜になる」等の
   非受動を検討し、それも不自然なら受動のまま残す。リファレンス文体自体
   が受動を呼ぶので、基準値超過分だけ直せば足りる。全滅させない。
6. **モダリティは意味で訳し分ける** — 許可(may)は「〜してよい/〜を
   認める」、義務(must)は「〜が必要だ/〜を必須とする」、推奨(should)
   は「〜を推奨する」。「〜できる」に崩してよいのは能力(can)の意味の
   ときだけ。許可・義務を「できる」に落とすと意味が変わる。
7. **緩衝を補う** — 「という」等が皆無で断定が連打されていたら、引用・
   命名・内容節が元から存在する箇所に限って補い、文末のリズム(〜する。
   〜する。〜である。)の単調さを崩す。密度を上げる目的で挿入しない。
8. **敬体/常体を統一** — 混在フラグが出ていたら文書の性格に合う方へ。

意味保存の回帰例(書き直し後にこの種の変化がないか自己点検する):

> 入力: root または所有者が実行できる
> NG:   root、所有者が実行できる   (OR が AND に読める)
> OK:   root か所有者が実行できる

> 入力: この操作は省略してもよい
> NG:   この操作は省略できる       (許可が能力に変わる)
> OK:   この操作は省略してよい

> 入力: 秘密鍵を共有すべきではない
> NG:   秘密鍵の共有を推奨する     (禁止が推奨に反転する)
> OK:   秘密鍵を共有しないことを推奨する

> 入力: 1台に対して2個を割り当てる
> NG:   1台へ2個を割り当てる       (比率の「に対して」は「へ」ではない)
> OK:   1台につき2個を割り当てる

やってはいけないこと:
- コードブロック・コマンド・識別子・数値・URL を変えない。
- 技術的な内容の追加・削除・「改善」をしない(それは別の依頼)。
- マーカーをゼロにすることを目的化しない。値が許容上限(warn)以上なら
  要修正と判定する。許容上限未満の文書を C 参照値へ寄せる修正はしない。
- マーカーを減らすために論理関係(AND/OR)やモダリティ(許可/義務/推奨/
  能力)を変えない。減らせない文はそのまま残すのが正しい。

### 4b. 検証待ちの指針

検証済みの修正順とは根拠の水準が違う。測定にも判定(フラグ・終了コード)
にも使わず、書き直しの際の目視観点としてのみ用いる。

- **詰まりの解消**(未検証・2026-08 の目視レビュー由来) — スクリプトが
  補助判定「詰まり」として、長文(120 字以上)・括弧の挿入が 2 回以上
  ある文・散文中の矢印記号(→)を報告する。長文は分割か並列内容の箇条
  書き化、括弧は本文への繰り込みか文の分離、矢印は「A だったが B に
  なった」のように文で書く。閾値は経験値で、終了コードには影響しない。
  機械検出できない詰まりも目視で点検する: 異なる事実が多数詰まった
  段落は箇条書きへ、用語が定義より先に使われていたら順序を入れ替える。
- **参照の局所化**(未検証・2026-08 の観察由来) — 「前述の」「この修正」
  が数段落前を指す長距離参照は、読者ではなく書き手の記憶モデルで較正
  された疑いがある。指す先が遠ければ言い直すか対象を名指す。速報測定
  では AI 書き下ろしの前方参照が人間翻訳の約 3 倍だったが、人間書き
  下ろしの対照群が無く未決着。過剰適用すると名詞の連呼になるので、
  参照先が直前の段落にあるものまで言い直さない。

検証が済んだら、この節の項目は修正順へ昇格させるか削除する。

### 5. 検証 (after)

Claude Code:

```bash
node ${CLAUDE_SKILL_DIR}/scripts/analyze.mjs 書き直したファイル
```

Codex:

```bash
node "<skill-dir>/scripts/analyze.mjs" 書き直したファイル
```

- before/after のマーカー密度を表で対比して見せる。
- 手順 3 の事実チェックリストと突き合わせ、落ちた情報がないか確認する。
  落ちていたら書き直しに戻す。
- 元ファイルを直接上書きせず、diff を示すか別ファイルに書いてユーザーに
  選ばせる(明示的に上書き指示がある場合を除く)。

## 背景データ

基準値は 2026-08 の対照実験に由来する。3条件(A: 別題材の技術文書を指示
のみで書き下ろし / B: 英語 man ページを翻訳 / C: B と同題材のリファレンス
を日本語で書き下ろし)+ 人間翻訳(H: JM プロジェクトの和訳 man。find/tar
の 2 文書のみ)。散文量は A/B/C 各約 1.5 万字、H 約 1.1 万字。

要点:
- 動作の名詞化は条件間で差がなかった。英語の義務的要素(主語スロット・
  if 節・前置詞・接続詞・法助動詞)に対応するマーカーが B 群で一貫して
  増えており、その持ち込みを主因の有力な作業仮説とする。
- 受動の多さは約半分がリファレンスというジャンル由来とみられる (C にも
  学習経由の翻訳文体が混じりうるため、ジャンル寄与は上限値)。
- 文頭指示語・「場合」・複合助詞・モダリティ硬直は人間翻訳者も同様に写す
  (翻訳一般の癖)。「および」・ジャンル水準を超える受動・「という」等の
  緩衝装置の欠落は AI 翻訳に偏る癖。
- したがって「人間翻訳並み」は目標にならない。目標は書き下ろし水準。
